사내 인시던트 티켓에서 배치 잡이 같은 결제 건을 두 번 처리했습니다. 로그를 보니 워커 A가 처리중이었고, 스케줄러는 A가 죽은 줄 알고 워커 B에게 같은 작업을 재할당했습니다. 그런데 A는 죽은게 아니라 GC로 인해 40초 정도 멈춰있었습니다.

이때 워커 A는 자기가 40초 동안 멈춰있었다는 걸 알 수 없습니다. A 입장에서는 시간이 흐른적이 없고, 본인이 여전히 그 작업의 소유자라고 믿으며 깨어나서 하던 일을 그대로 이어갑니다. 그리고 스케줄러 입장에서도 A가 죽었는지, 느린 건지 구분할 방법이 없습니다.

분산 시스템에서 "누가 무엇을 담당하는가"를 확실하게 정하는 일이 왜 그렇게 어렵고, 왜 그렇게 비싸고, 애초에 그걸 정하지 않아도 되게 만드는 방법은 무엇일까요?

# 부분 장애
단일 머신에서는 함수 호출 시 성공 or 예외 2가지의 경우만이 존재합니다. 프로세스가 죽는 경우도 있지만, 그때는 호출한 쪽도 같이 죽습니다. 때문에 <b>"결과를 모른 채 살아서 다음 결정을 내려야 하는 상황"</b>이 발생하지 않습니다. 하지만 분산 환경에서는 <b>"모름"</b>이라는 제3의 상태로 호출이 진행될 경우가 생깁니다.

### 뭘 모를까?
요청을 보냈는데 응답이 없다면, 노드간 다음과 같은 6가지 상황이 전제될 수 있습니다.
1. 요청이 네트워크에서 유실됨
2. 요청이 상대방 큐에서 대기 중
3. 상대 노드가 죽음
4. 상대 노드가 일시적으로 멈춤
5. 응답이 유실됨
6. 응답이 지연 중

타임아웃 만으로는 이 6가지 상황을 구분할 수 없습니다.

특히 3, 4번의 차이가 치명적입니다. 죽은 노드는 아무 일도 안하지만, 멈춘 노드는 깨어나서 하던 일을 계속 하게 됩니다. 위에서 설명한 워커 A가 해당 케이스이구요.
5번도 문제가 되는데, 작업은 수행했는데 응답만 유실된 경우 이를 재시도하면 이중 실행이 됩니다. 결제 도메인에서는 최악의 경우이고, 이 부분이 멱등성이 필요한 이유입니다.

> "그럼 타임아웃을 잘 잡으면 되는거 아님?"

이것도 트레이드오프가 있는데,
만약 타임아웃을 길게 잡으면 진짜 죽은 노드를 오래 방치하게 되고, 사용자는 그만큼 오래 기다려야 합니다. 타임아웃을 짧게 잡으면 살아있는 노드를 죽었다고 오판해서 작업이 중복 실행되고, 이미 부하가 높은 시스템에 부하를 더 얹어서 연쇄 장애로 번질 수 있습니다.

네트워크 지연에는 상한이 없습니다. 그리고 그 원인은 대부분 큐잉 지연입니다.
- 여러 노드가 동시에 같은 목적지로 보내면 스위치 큐가 쌓이고, 꽉 차면 패킷을 버림
- 수신 노드 CPU가 바쁘면 OS 큐에서 대기
- 가상화 환경에서는 VM 자체가 수십 ms 멈춤
- TCP 재전송이 지연을 더 늘림

전화망의 경우는 회선 교환이라 통화 시작 시 대역폭을 예약해서 지연이 일정합니다. 하지만 인터넷은 패킷 교환이라 대역폭을 동적으로 나눠씁니다. 웹 요청은 순간적으로 몰렸다 없어졌다 하기 때문에, 버스트 트래픽에 최적화된 방식을 택한거죠.

그래서 가변적 지연은 자연 법칙이 아니라 여러 트레이드오프의 결과입니다. 고칠 수 있는게 아니라 선택할 수 밖에 없던거죠. 때문에 정확한 타임아웃 최적값은 계산할 수 없습니다.

### 프로세스는 왜 멈추는가
실행중인 스레드는 다음의 경우와 같이 어느 지점에서든 임의로 오래 멈출 수 있습니다.
- **GC STW**(stop-the-world)
- VM 서스펜드 / 라이브 마이그레이션 - VM이 통째로 정지했다 다른 호스트에서 재개
- CPU 스틸 - 멀티테넌트 환경에서 다른 VM에 CPU를 뺏김
- 스와핑 / 페이지 폴트
- 동기 디스크 I/O
- SIGSTOP

다음은 `lease` 기반 리더 체크 예시입니다. `lease`, 즉 만료 시간이 있는 락으로 자신이 담당자인이 확인하는 흔한 패턴입니다.
```java
while (true) {
    request = getIncomingRequest();
    
    // 리스 만료가 10초 이내면 갱신
    if (lease.expiryTime - System.currentTimeMillis() < 10000) {
	    lease = lease.renew();
    }
    if (lease.isValid()) {
        process(request);   // ← 여기 도달하기 전에 멈췄다면?
    }
}
```
이 경우 `isValid()`가 true를 반환한 시점과 `process()`가 실제로 실행되는 시점 사이에 노드가 멈출 수 있습니다. 그럼 노드는 더이상 `renew()`로 연장을 요청하지 못하고 TTL 이후 자동으로 리더 자격을 상실합니다. 로직적으로는 **"확인했다"와 "여전히 유효하다"가 다른 얘기**가 되는거고, 시스템적으로는 노드 중지로 인한 요청 재처리, 유실 방지, 리더 재선출, 스플릿 브레인 등의 여러 작업 및 오류 상황이 가정됩니다.

#### 진실은 다수결이 결정한다
이렇게 다양한 장애 지점이 존재하기 때문에, 노드 간 일관성을 위한 원칙이 필요합니다. 한 노드는 스스로 아무것도 확신할 수 없습니다. 자기 상태만 알고, 남의 상태는 메시지로 추측할 뿐입니다.

그래서 진실은 개별 노드가 아니라 **정족수(quorum)가 결정합니다.** 노드가 "나 살아있어"라고 주장해도, 과반이 "쟤 죽었어"라고 판정하면 죽은 거죠.

그렇다면 질문은 이렇게 바뀝니다. "누가 살아 있고 누가 무엇을 담당하는가"에 대한 정족수의 결정을 어떻게 안전하게 운영할 것인가. 이것이 **합의(consensus)** 문제입니다.


# 합의
### 합의란 무엇인가
합의는 여러 노드가 하나의 값에 동의하게 만드는 문제입니다. 추상적으로 들리지만 실무에서 가장 필요한 지점이라고 생각합니다. 리더가 정확히 하나여야 한다, 락의 소유자가 한 명이어야 한다, 같은 사용자명으로 두 명이 가입하면 안 된다, 여러 노드에 걸친 트랜잭션은 전부 커밋되거나 전부 취소돼야 한다. 모두 "여러 노드가 같은 결정을 내려야 한다"는 문제이고, 결국 합의로 환원됩니다. 도입부의 "작업 X의 담당자는 누구인가"도 마찬가지입니다.

### 2PC의 한계
여러 노드가 같이 결정하는 고전적인 방법은 2단계 커밋(2PC)입니다.

>[!2PC 프로세스]
> ##### 1단계 (준비)
>- 코디네이터: "다들 커밋 가능하시죠?"
>- 참여자들: "YES"
>
>→ 참여자들은 커밋 응답 이후로 응답 수정은 불가능하며, 코디네이터 결정을 대기
>##### 2단계 (커밋)
> - 코디네이터: 결정을 자기 로그에 기록
> - 코디네이터: "커밋하세요"
> 
> → 코디네이터는 참여자 전원이 커밋할 때 까지 무한 재시도

문제는 참여자가 YES를 보낸 뒤 코디네이터가 죽는 경우입니다. 참여자는 이미 커밋하겠다고 약속했으니 혼자 취소할 수 없고, 코디네이터의 결정을 모르니 혼자 커밋할 수도 없습니다. 이 상태를 in-doubt라고 부르는데, 참여자는 그동안 락을 쥔 채 무기한 기다리고, 그 데이터를 건드리려는 다른 트랜잭션도 전부 막힙니다. 코디네이터가 복구될 때까지 시스템이 멈추는 것이니, 코디네이터가 단일 장애점(SPOF)인 셈입니다. 근본 원인은 2PC가 **전원의 동의를 요구**한다는 데 있습니다. 한 명만 응답이 없어도 진행할 수 없습니다.

### 합의 알고리즘
Paxos, Raft, Zab 같은 합의 알고리즘은 이 문제를 전원 대신 과반으로 해결합니다. 합의 알고리즘이 만족해야 하는 성질은 네 가지입니다.

- 두 노드가 서로 다른 값을 결정하지 않아야 함 (균일 동의)
- 한 번 결정한 값을 바꾸지 않아야 함 (무결성)
- 결정된 값은 누군가 실제로 제안한 값이어야 함 (유효성)
- 죽지 않은 노드는 결국 결정에 도달해야 함 (종료)

마지막 종료 성질이 2PC와의 결정적 차이입니다. 5노드 클러스터라면 3노드만 살아 있어도 진행이 됩니다.

동작 방식은 대략 이렇습니다. 노드들이 리더를 뽑고, 리더를 뽑을 때마다 단조 증가하는 에포크(epoch) 번호를 붙입니다. 리더가 값을 제안하면 과반이 투표해 승인하고, 과반이 승인하면 그 값이 확정됩니다. 리더가 죽은 것 같으면 더 높은 에포크 번호로 새 선거가 열립니다.

참고로 "값을 제안한다" 에서 값은 **시스템의 상태를 바꾸는 모든 명령이나 데이터**를 가리킵니다. 예시로, 분산 DB에서는 "사용자 A의 계좌 잔액을 **10,000원**으로 수정한다." 같은 경우가 될 수 있고, 복제 로그의 경우에는 "로그 45번에 **'데이터 삽입(Insert)' 명령**을 기록한다." 와 같은 명령이 노드가 제안하는 "값"에 해당합니다.

여기서 중요한 것은 투표가 두 번 일어난다는 점입니다. 리더를 뽑을 때 한 번, 리더의 제안을 승인할 때 한 번. 그리고 두 과반 집합은 반드시 최소 한 노드 이상 겹칩니다. 그래서 옛 리더가 멈췄다 깨어나 제안을 해도 그 제안을 승인할 과반을 모을 수 없습니다. 과반 중 적어도 한 노드는 이미 더 높은 에포크의 리더가 있다는 사실을 알고 있고, 낮은 에포크의 제안을 거부하기 때문입니다. 두 리더가 동시에 존재하는 스플릿 브레인이 원리적으로 차단됩니다.

### 펜싱 토큰
합의 알고리즘은 합의 시스템 안에서의 스플릿 브레인을 막아 줍니다. 하지만 도입부에 말했던 사건은 합의 시스템 밖, 결제를 기록하는 DB에서 일어났습니다. 깨어난 워커 A가 결제를 기록하려 할 때 누군가 "너는 더 이상 담당자가 아니다"라고 말해 줘야 합니다. 그 장치가 <b>펜싱 토큰(fencing token)</b>입니다.

아이디어는 단순합니다. 락이나 작업 할당을 줄 때마다 단조 증가하는 번호를 함께 발급하고, DB는 자신이 이미 본 번호보다 작은 번호가 붙은 쓰기 요청을 거부합니다.

핵심은 검사를 DB 쪽에서 한다는 겁니다. 워커 A에게 스스로 판단하게 하면 안 됩니다. A는 자기가 멈췄다는 사실을 모르기 때문에! 실제로 ZooKeeper의 트랜잭션 id(zxid)나 순차 노드 번호, etcd의 리비전이 이 역할을 합니다. 반대로 Redis의 `SET NX EX` 기반 분산 락에는 이런 토큰이 없어서, 락이 TTL로 만료된 뒤 깨어난 클라이언트를 막을 방법이 없습니다. **중복 실행이 단순히 낭비 정도의 작업이면 Redis 락으로 충분하지만, 중복 실행이 데이터를 망가뜨리는 작업이라면 펜싱이 가능한 수단이 필요**합니다.

그런데 DB가 펜싱 토큰을 검사할 수 있다는건 결국 `WHERE fence < :token` 같은 원자적 조건부 쓰기를 지원한다는 뜻인데, 그럼 애초에 복잡하게 분산 락을 걸 필요가 없지 않을까요? 그냥 DB에 저 SQL만 날리면 알아서 원자적으로 처리되는데..?

실제 펜싱 토큰 검사 예제는 다음과 같이 조건부 UPDATE로 구현됩니다.
```sql
UPDATE payments
	SET status = 'COMPLETED', fence = :token 
WHERE payment_id = :id
	AND fence < :token;
```

여기서는 "그럴거면 락 왜씀?" 이라는 경쟁적 질문보다 각 기술이 커버하는 지점을 파악해야 합니다. Redis 등의 분산 락은 잘못된 외부 호출을 차단하지만, 버그나 네트워크 지연 등 외부 요소들로 인해 스플릿 브레인이 언제든 생길 수 있기도 합니다. 때문에 락을 쓰든 안 쓰든 결국 **데이터 정합성은 최종적으로 DB단에서 원자적 검증(조건부 쓰기, 트랜잭션 등)으로 지켜야 한다**는 뜻 입니다.

### 합의 비용
합의는 모든 결저에 과반의 응답을 기다려야 하니 본질적으로 동기 복제이고, 그만큼 느립니다. 1대의 장애를 견디려면 최소 3노드, 2대를 견디려면 5노드가 필요합니다. 참여 노드 집합이 고정적이라 노드를 동적으로 추가하거나 빼는 일이 까다롭고, 장애 감지가 타임아웃에 의존하니까 네트워크가 불안정하면 멀쩡한 리더를 죽었다고 판단해서 성능 저하의 원인이 되기도 합니다.

더 근본적인 비용은, 합의 위에 세울 수 있는 강한 일관성 모델인 선형성(linearizability), 즉 시스템에 데이터 사본이 하나만 있는 것처럼 보이게 하는 보장은 응답 시간이 네트워크 지연에 영향을 받을 수 밖에 없습니다. 멀티코어 CPU조차 기본적으로 선형적이지 않은데, 코어마다 캐시를 둬서 성능을 확보하는 대신, 다른 코어의 쓰기가 즉시 보이는 것을 포기했기 때문입니다. **강한 일관성을 포기하는 이유는 보통 장애 내성 보다는 성능의 이유**가 큽니다.

그래서 실제 시스템들은 ZooKeeper나 etcd 같은 코디네이션 서비스 3~5 노드에만 합의 알고리즘을 적용해서, 누가 리더인지, 누가 살아있는지, 어느 파티션을 누가 담당하는지 처럼 작고 잘 바뀌지 않는 메타데이터만 둡니다. 실제 데이터는 그 결과를 소비하는 수백, 수천 개의 노드가 **합의를 적용하지 않고 빠르게 처리**합니다. 

대표적인 예시는 다음과 같고, 이 아키텍처들의 모양이 모두 합의 비용으로 인해 정해진 것입니다.
- **Kafka:** 컨트롤러(메타데이터 관리)와 브로커(데이터 처리)
- **HDFS:** NameNode(메타데이터)와 DataNode(데이터 저장)
- **Kubernetes:** etcd(메타데이터)와 kubelet(실행 담당)

### CAP
합의 비용 문제를 가장 잘 요약한 예시가 CAP 정리입니다. 보통 일관성(Consistency, C), 가용성(Availability, A), 분단 내성(Partition Tolerance, P) 중 둘만 고를 수 있다고 하지만, 네트워크 분단이라는건 고를 수 있는 항목이 아닙니다. 분산 시스템은 여러 대의 컴퓨터가 네트워크로 묶여 있기 때문에, **네트워크 분단은 언젠가 반드시 발생**합니다. 인간이 네트워크 케이블이 뽑히거나 라우터가 죽는 걸 완전히 막을 수는 없으니까요.

따라서 **P는 선택의 여지없이 무조건 전제**해야 하므로, 실질적으로는 **네트워크가 끊겼을 때(P 상황에서) 일관성과 가용성 중 무엇을 포기할 것인가**의 문제입니다.

#### 1. CP 시스템 (Consistency + Partition Tolerance)
- **선택:** 네트워크가 끊기면 일관성을 유지하기 위해 응답을 거부(또는 대기)
- **특징:** 틀린(오래된) 데이터를 보여주느니 차라리 에러를 내거나 응답을 멈추는 방식
- **대표 예시:** ZooKeeper, etcd, HBase, MongoDB (기본 설정)

#### 2. AP 시스템 (Availability + Partition Tolerance)
- **선택:** 네트워크가 끊겨도 시스템이 멈추지 않고, 각자 살아있는 노드가 **일단 응답**
- **특징:** 노드 간 동기화가 안 되었기 때문에 서로 다른 노드에서 서로 다른(오래된) 데이터가 응답할 수 있음
- **대표 예시:** Apache Cassandra, Amazon DynamoDB

### PACELC
CAP는 분단 상황만 다룬다는 한계가 있습니다. 이를 보완한 것이 PACELC입니다. 분단(P)시에는 가용성(A)와 일관성(C) 중 하나를, 그 외(E)의 평상시에는 지연(L)과 일관성(C) 중 하나를 고른다는 뜻입니다.

분단 상황은 드물지만 지연과 일관성의 트레이드오프는 모든 요청에 존재합니다. 읽기를 가까운 복제본으로 보낼지, 최신 값을 가진 리더까지 왕복할지가 이런 ELC 트레이드오프에 해당합니다.

# 불변성과 멱등성
위에서 결국 데이터 정합성을 지키는 최종 단계는 DB단의 원자적 검증이라고 했습니다. 그렇다면 순서를 뒤집어서, 락이나 합의 인프라를 들이기 전에 저장소가 이미 가진 원자적 장치로 문제가 풀리는지부터 확인해봐야겠죠?

우선 중복 제거의 문제는 **UNIQUE 제약**을 사용합니다. 결제 건마다 청구 기록이 하나만 있어야 한다면, 그 사실을 DB에 선언하면 됩니다. 이러면 동시에 두 워커가 INSERT해도 하나만 성공하고, 나머지는 제약 위반으로 실패합니다.
```sql
CREATE UNIQUE INDEX ux_payment_charge ON payment_charges (payment_id);
```

"조건을 만족할 때만 바꾼다"는 유형은 **조건부 UPDATE**로 넣고, 원자적으로 처리합니다. 확인과 갱신 모두 한 문장에 넣는 방식입니다.
```sql
UPDATE payments
	SET status = 'COMPLETED'
WHERE payment_id = :id
	AND status = 'PENDING';
```

위의 두 장치는 서버가 몇 대든 상관없이 동작하고, 별도의 락 서버가 죽어도 영향이 없고, 만료 시간에 대한 고민도 없습니다. 대신 외부 결제 API나 메일 발송, 파일 생성 등 대상이 DB 외부에 있을 때나 여러 시스템을 거치는 긴 작업을 동시에 하나만 돌려야 할 경우는 위의 경우로는 부족합니다. 그런 경우에도 DB가 할 수 있는건 최대한 DB에 맡기고, 나머지 역할을 최소화하는 방향으로 설계를 해나가야 합니다.

### 애초에 충돌을 없애라
같은 자원을 동시에 건드리려고 하면 충돌이 일어납니다. 그럼 같은 자원을 안 건드리게 하면 되는거 아닐까? 라는 생각으로 생겨난 기술들이 있습니다. LSM 트리는 값을 덮어쓰지 않고 새 세그먼트를 추가한 뒤 나중에 병합하고, MVCC는 값을 수정하는 대신 새 버전을 만들고, 합의 알고리즘도 내부적으로는 추가만 가능한(append-only) 로그를 복제합니다. 

위의 기술들에서, 각 값들은 **건드려질 일이 없기 때문에 불변성을 유지**하게 되고, 분산 시스템에서는 이런 원리가 매우 중요한 설계 지점이 됩니다. 설계 하나만으로 각 값들이 그 순간에 기록된 100% 정확한 값임을 보장할 수 있고 이를 통해 합의를 좀 더 원활하게 할 수 있는거죠.

### 배치
MapReduce나 Spark 같은 배치 시스템은 입력 파일을 절대 수정하지 않고, 결과를 항상 새로운 위치에 기록합니다. 그래서 Task가 실패하면 프레임워크가 그냥 다시 실행합니다. 입력은 그대로고, 연산도 동일한 함수를 재실행 하는 거니까 몇 번을 실행해도 같은 결과를 보장합니다. 멈췄다 깨어난 Task가 뒤늦게 결과를 기록하려해도, 그 결과는 이미 버려진 임시 경로에 쓰일 뿐이라 아무런 영향이 없습니다.

휴먼 에러에도 대응이 가능합니다. 코드에 버그가 있어서 잘못된 결과가 나왔어도, 원본 입력 데이터가 그대로 남아있기 때문에 코드를 고쳐서 재실행하면 정확한 값으로 복구가 가능합니다. 대신 연산 자체가 결정적이어야 합니다. `rand()`나 `now()`, 외부 API 호출처럼 실행할 때마다 달라지는 요소가 있으면 원본이고 뭐고 재실행 결과는 신뢰할 수 없으니까요.

### 이벤트 로그
배치의 입력이 유한한 파일이라면, 지속적으로 발생하는 스트리밍 데이터에 같은 원리를 적용한 것이 이벤트 로그입니다. Kafka 같은 로그 기반 시스템은 이벤트를 append-only 로그에 쌓고, 컨슈머는 자신이 어디까지 읽었는지를 나타내는 오프셋만 기억합니다. 컨슈머에 버그가 있었다면 오프셋을 되감아서 재처리가 가능합니다.

**이벤트 소싱**은 여기서 한 걸음 더 나아가서, **결과 값(가변 상태) 대신 "무슨 일이 일어났는가" 라는 이벤트(불변의 사실)만 저장**합니다. 현재 잔액을 저장하지 않고 입금과 출금 이벤트를 저장한 뒤, 잔액은 이벤트를 차례로 적용해서 계산합니다. 

이렇게 하면 결과 값은 원본이 아니라 파생물이 됩니다. 이벤트 로그가 원본이 되기 때문에, 같은 이벤트 로그에서 검색 색인, 캐시, 분석용 테이블 모두 만들 수 있고, 새로운 뷰가 필요하면 기존 뷰를 건드리지 않고 로그를 쭉 읽으면서 새로운 뷰를 만들어 주면 됩니다.

**CQRS(Command Query Responsibility Segregation) 패턴**이 이런 원리를 기반으로 합니다. 명령 모델(Command Side)과 조회 모델(Query Side)을 분리해서 이벤트를 쌓고 조회용 테이블을 따로 분리하면, 쓰기와 읽기가 완전히 독립되어 있어서, 아무리 조회가 폭발해도 쓰기(결제/입금) 시스템은 마비되지 않는거죠.

### 멱등성

<div class="callout-box" data-callout="note">
<div class="callout-box-title"><span class="callout-box-icon">🗒️</span>멱등성(idempotency)</div>

같은 연산을 여러 번 실행해도 한 번 실행한 것과 결과가 같은 성질

</div>


결제 처리는 본질적으로 외부 API와 통신하는 것이고, PG사의 API는 제가 발급한 펜싱 토큰 같은건 알 수 없습니다. 지금까지의 시스템 내부적인 해결은 통하지 않는거죠. 여기서 필요한 것이 멱등성입니다.

펜싱과는 좀 다른 방향인데, 펜싱이 두 번째 실행을 막으려고 하는거면, 멱등성은 두 번째 실행이 일어나도 아무 일도 일어나지 않게 만듭니다.

가장 흔한 구현은 작업마다 고유한 멱등성 키를 부여하고, 그 키로 이미 처리된 작업인지 확인하는 것입니다. PG사 API가 멱등성 키를 지원하는 것도 이 점 때문입니다.

서비스 DB에는 `(사용자 ID, 멱등성 키)`에 **유니크 제약**이 있는 멱등성 기록(`idempotency_record`)을 둡니다. 요청이 오면 먼저 기록을 원자적으로 등록하고, 이미 같은 키가 있으면 저장된 요청 내용과 결과를 확인합니다. 같은 내용의 요청이 이미 완료됐다면, PG사를 다시 호출하지 않고 이전 결과를 반환합니다. 같은 키에 다른 결제 내용이 들어오면 요청을 거부합니다.
```sql
INSERT INTO idempotency_record
	(user_id, idempotency_key, request_hash, status, updated_at)
VALUES
	(?, ?, ?, 'PROCESSING', NOW());
```

INSERT에 성공한 요청만 이 기록을 커밋 후 PG사를 호출합니다. PG사에도 같은 멱등성 키를 전달하므로, 호출을 재시도해도 중복 청구되지 않습니다.

```java
gateway.charge(
	amount,
	idempotencyKey
);
```

멱등성 기록의 상태 전이도 조건부로 처리해서, 이미 완료된 요청은 다시 완료 처리되지 않도록 합니다.

```sql
UPDATE idempotency_record
	SET status = 'COMPLETED',
		response_json = ?,
		updated_at = NOW()
WHERE user_id = ?
	AND idempotency_key = ?
	AND status = 'PROCESSING';
```

이러면 두 워커가 동시에 같은 결제를 처리하더라도 DB 유니크 제약으로 멱등성 기록은 하나만 만들어집니다. 한 워커가 먼저 처리했다면 다른 워커는 그 기록을 읽고 진행 중 상태를 따르거나, 완료 결과를 반환합니다. 도입부의 워커 A처럼 멈췄던 워커가 뒤늦게 깨어나 같은 결제를 처리하더라도, PG사는 같은 키를 보고 중복 청구하지 않고, 이미 완료된 결제의 조건부 업데이트는 0행을 변경합니다.

흔히 말하는 "정확히 한 번(exactly-once)" 처리도 진짜로 한 번만 실행하는게 아니라, 최소 한 번(at-least-once) 실행하되 멱등하게 만들어 결과가 한 번 실행한 것과 같아지도록 하는 것입니다.

## 결론
**펜싱 토큰**은 합의로 발급한 단조 증가 번호로 옛 담당자의 쓰기를 막습니다. 정확하지만 합의 인프라와 토큰을 검사해 줄 자원이 필요합니다. **멱등성**은 중복 실행을 막지 않는 대신 무해하게 만듭니다. 지연이나 인프라 조율 비용은 없지만, 설계 자체에 대한 비용이 들어갑니다.

각 특성에 맞춰서 시스템은 위 기술을 적절히 나눠 활용합니다. 누가 리더이고 어떤 파티션을 누가 담당하는지 같은 작은 메타데이터는 합의로 강하게 조율하고, 대량의 실제 데이터 처리는 불변 입력과 멱등한 연산으로 빠르게 병렬 처리합니다. 조율 과정은 비싸니까 좁은 영역에서만 활용하고, 나머지는 이런 조율 비용이 필요 없는 구조로 만드는 거죠.

분산 시스템에서 "확실히 알고 있다"라는 대답은 존재하지 않습니다. 그 불확실성을 합의로 정면돌파할거냐 아님 불변성으로 우회할 것이냐. 좋은 설계는 둘 중 하나를 고르는게 아니라, 어디서 뭘 쓸지 정확히 구분하는데서 시작합니다.
